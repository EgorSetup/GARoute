# GARoute — правила работы агента

## Текущие полномочия

2 ноября 2026 пользователь отдельным сообщением разрешил реализацию всего проекта и поручил начать с T00.01. Прежнее ограничение «только документация» снято. Порядок задач, открытые решения категории C и проверки из этого файла остаются обязательными.

## Постоянные решения

- GARoute (Genetic Algorithm Route), каталог `C:\GARoute`, GitHub-репозиторий `GARoute`, основная ветка `main`.
- Приоритет: последние прямые указания пользователя → полный исходный диалог → принятые DECISIONS.md → остальные документы → технические рекомендации. Не восстанавливать требования из памяти вместо этих документов.
- После этапа 0 — UI-first: сначала NiceGUI + Leaflet, затем OSM, особи, Fitness, операторы, эволюция, пробки, визуализация.
- Утверждённые модули: data/, algorithm/models.py, algorithm/genetic/, algorithm/evaluation/, interface/, visualization/, tests/. Не заменять их другой архитектурой.
- Гены — направленные рёбра (u,v,key). Недопустимые особи отбраковываются; ремонта сейчас нет. Предусмотреть локальное место подключения ремонта без переписывания основного цикла.
- Популяция строго N; лимит копий; конечные попытки. Ошибка генерации не доказывает отсутствие маршрута.
- Пробки 1–11; 11 закрывает ребро только по принятому правилу эффективного уровня. Выбор сегмента — наибольшая длина покрытия, при равенстве больший балл. Не заменять это максимумом пробки по всем касаниям.
- Экономичный = кратчайший; числа OPEN/PROPOSED нельзя придумывать или активировать как defaults; Q — идентификатор группы, не статус. Ни один пример из макета не становится default без решения.
- Эталоны нормализации неизменны в запуске. Жёсткие запреты не заменять штрафами.
- Сначала расчёт истории, затем воспроизведение. Перемотка не вызывает ГА.
- Переключение пресета сохраняет результаты. Изменение общих условий сначала требует подтверждения в приложении; отмена ничего не меняет, подтверждение очищает результаты/графики/поколения. Это требование к продукту, а не запрос повторного разрешения агенту на каждую правку кода.

## Уточнения аудита 1.1

- ACCEPTED A — восстановленное согласование; ACCEPTED / TECHNICAL B — внутренняя детализация по текущему разрешению; OPEN C — нужен ответ пользователя. Не задавать повторно вопросы A/B. Полный список и обоснования — DECISIONS.md; при продолжении читать только нужные подпункты.
- Приняты турнир 3, N=10 и UI-диапазон 5–50, начальный предел 3×L_min. Базы новичка L_min/T_min не заменять нормализацией. Окно стагнации 10 остаётся PROPOSED, общая P0 также PROPOSED. Не применять их до ответа.
- После UI-каркаса пройти раннюю контрольную точку существующего ядра T06.01 с тестовой функцией оценки/стратегией весов. Это не полная производственная реализация; закрытие параметризованного модуля не означает закрытие его поздней интеграции.
- Не создавать отдельное приложение или тестовую ветвь алгоритма. Ядро принимает простые функции/данные, тесты задают искусственные числа. Производственную стратегию подключать только после Q06-C.
- J разных пресетов не сравнивать как общую шкалу качества, даже при одинаковых эталонах. Сравнивать L/T/C. Общие условия включают custom-веса; фиксированный пресет и параметры показа исключены.
- В PROGRESS раздельно записывать доказательства теста ядра, реального OSM и UI; нельзя заменять один вид проверки другим.

## Восстановление контекста

1. Прочитать AGENTS.md, CURRENT_TASK.md и только блок «Текущее состояние» PROGRESS.md.
2. Открыть карточку активного ID в IMPLEMENTATION_PLAN.md, строки её зависимостей и нужные записи DECISIONS.md.
3. Прочитать только указанные разделы SPEC.md и затрагиваемые файлы/контракты. Пользоваться поиском по ID/символам.
4. Проверить реальное состояние файлов и Git: журнал не доказывает отсутствие новых пользовательских изменений.
5. Не перечитывать всю беседу, весь SPEC.md, весь план и все исходники после каждого продолжения. Расширять чтение только если текущий контекст неполон, контракт изменился или проверки указали на проблему.

## Цикл одной задачи после разрешения реализации

1. Выбрать TODO-задачу с выполненными зависимостями и решёнными нужными C-подпунктами Q. После T01.09 приоритет имеет ранняя цепочка до T06.01 из плана, затем обычная интеграция; числовой порядок ID не заменяет зависимости. Если текущая IN_PROGRESS — сначала восстановить её.
2. Перенести её краткую карточку в CURRENT_TASK.md: ID, `/цель`, входы, точные файлы, контракты, действия, проверки и следующий шаг. Отметить IN_PROGRESS в реестре плана.
3. Если инструмент целей доступен, создать одну цель на эту задачу; закрывать её только при выполненных критериях. При отсутствии инструмента достаточно строки `/цель` в рабочем файле. Не заводить одновременно конкурирующие цели.
4. Проверить вводные. При нехватке принципиального решения записать BLOCKED и задать один конкретный вопрос с простым/расширенным вариантом, не подменять ответ пользователя догадкой. Продолжать независимые готовые задачи, если такие есть.
5. Реализовать минимальное законченное изменение в пределах карточки. Понятные функции, типы, русские docstring и комментарии к неочевидному. Без спагетти-кода и абстракций ради абстракций.
6. Проверить целевые тесты/сценарии и просмотреть diff. Ошибки исправлять локально. Не запускать широкий повторный прогон без причины, кроме предусмотренных контрольных этапов.
7. После фактического успеха отметить чеклисты и DONE; добавить краткое доказательство в PROGRESS, обновить матрицу и текущую задачу. Не считать написанный код автоматически проверенным.
8. Сделать осмысленный коммит с ID после просмотра staged diff, затем выбрать следующую готовую задачу. Пользователь не должен каждый раз подтверждать обычные обратимые изменения, уже разрешённые задачей.

## Git и публикация

- Этап 0 выполняется только после разрешения реализации. Перед созданием GitHub выяснить владельца/видимость Q12; не угадывать их.
- Не перезаписывать существующий каталог/репозиторий. Сначала проверить рабочее дерево, текущую ветку и remote.
- Коммиты небольшие и осмысленные, после проверки задачи; точечно добавлять файлы. Нельзя включать чужие несвязанные правки.
- Force push и принудительное переписывание опубликованной истории без отдельного явного разрешения запрещены. Секреты не публиковать. Не обходить ошибки push через сброс ветки.
- Первый обычный push и сверка SHA входят в этап 0. Режим последующих push установить явно; локальные регулярные коммиты не означают автоматическое разрешение любой внешней публикации.
- `.env`, ключи, виртуальное окружение, временные выгрузки OSM и кэши не публиковать. Проверять staged-состав, не только .gitignore.

## Рабочие файлы и статусы

- IMPLEMENTATION_PLAN.md — единственный реестр статусов задач: TODO / IN_PROGRESS / BLOCKED / DONE.
- CURRENT_TASK.md — короткий активный контекст; не накапливать в нём историю. Целевой размер — одна-две экранные страницы, технические детали при необходимости ссылками.
- PROGRESS.md — краткое актуальное резюме сверху, ниже журнал завершений/ошибок с проверками. Старые записи не перечитывать без причины.
- DECISIONS.md — ответы на Q с датой, источником и затронутыми задачами. Продуктовое предложение не отмечать как принятое без согласия. Технические детали категории B можно выбрать по разрешению текущего аудита, явно записав ACCEPTED / TECHNICAL, причину и проверки; это не историческое согласие пользователя.
- REQUIREMENTS_MATRIX.md — покрытие требований; реализация подтверждается доказательством, не наличием строки.
- Если сессия заканчивается посреди задачи, сохранить последний выполненный шаг, непройденную проверку и точную следующую команду/действие. Не ставить DONE ради красивого отчёта.

## Общение

Отвечать по-русски, кратко и конкретно. Сообщать, какие файлы действительно сохранены, что проверено и что осталось. При длительной работе давать короткие обновления по результатам; не выдавать планируемое за сделанное. При неизвестном ответе объяснять причину. Не повторять вопросы, на которые исходная беседа уже дала ответ.
