# GARoute — стартовый промпт для Codex

Этот текст предназначен для будущего запуска реализации после отдельного решения пользователя. Само наличие файла не разрешает начинать работу. Скопировать раздел ниже в новый запрос Codex, открыв `C:\GARoute` как рабочий каталог.

---

Приступай к пошаговой реализации **GARoute (Genetic Algorithm Route)** по подготовленной документации. Работай в `C:\GARoute`. GitHub-репозиторий называется `GARoute`, основная ветка — `main`.

Сначала прочитай `AGENTS.md`, `CURRENT_TASK.md` и раздел «Текущее состояние» в `PROGRESS.md`. Затем открой карточку текущей задачи в `IMPLEMENTATION_PLAN.md`, её зависимости и только связанные разделы `SPEC.md`, решения `DECISIONS.md` и строки `REQUIREMENTS_MATRIX.md`. Этот запрос разрешает переход от подготовки документов к реализации; не считай прежнюю отметку «только документация» вечным запретом после этой явной команды.

При конфликте приоритет таков: последние прямые указания пользователя → исходная беседа → принятые DECISIONS.md → документы → технические рекомендации. Технические решения B уже разрешены и помечены TECHNICAL; они не выдаются за прежние согласования.

Не начинай с чтения всего проекта и не перечитывай всё ТЗ после каждого шага. Восстанавливай контекст по коротким рабочим файлам. Если карточке не хватает контракта или решения, точечно прочитай соответствующий раздел/файл и дополни карточку. Исходная беседа — справочный источник для спорных согласований, а не обязательное чтение на каждом продолжении.

Порядок работы:

1. Проверь реальное содержимое каталога, Git-статус, ветку и remote. Не затирай чужие изменения. Если реализации ещё нет, начни с T00.01. Если работа уже идёт, продолжи активную задачу, не создавай проект заново.
2. Выполни этап 0: каталог, Git, .gitignore, GitHub GARoute, origin, первый осмысленный коммит и обычный push, сверка локального/удалённого SHA и ветки main. Перед созданием GitHub выясни Q12 — владельца и видимость; используй доступные подключённые инструменты, не угадывай аккаунт и не меняй глобальные настройки без необходимости.
3. После Git сначала создай интерфейсный каркас NiceGUI + Leaflet. Не начинай с полноценного алгоритма. После T01.09 сначала пройди раннюю цепочку ядра до T06.01 из плана на искусственном графе. Затем следуй интеграции граф → генерация → Fitness → операторы → эволюция → пробки → визуализация → итоговая проверка. Не создавай второе приложение; зависимости важнее числового порядка ID.
4. На каждой итерации выбирай одну задачу с уникальным ID, выполненными зависимостями и закрытыми относящимися к ней вопросами. Запиши в CURRENT_TASK.md её `/цель`, точные файлы, входы/выходы, действия и проверки. В плане отметь IN_PROGRESS. Если есть инструмент целей, веди одну активную цель и закрывай её только по результату; без него используй запись в файле.
5. Выполни минимальное законченное изменение. Основную логику пиши небольшими понятными функциями с типами, русскими docstring и комментариями к формулам/неочевидному. Не переписывай рабочие модули целиком и не меняй архитектуру ради удобства текущей задачи.
6. Проведи проверки из карточки. Для вычислительной логики используй маленькие графы с известными ответами и содержательные тесты. Для UI проверь реальный интерфейс, состояния и действия. Непроведённые проверки так и обозначай. Не отмечай задачу готовой, пока её критерии не доказаны.
7. Просмотри diff, обнови чеклисты/статус DONE, PROGRESS.md и матрицу покрытия. Сохрани краткое резюме: что изменено, чем проверено, что ограничено, какая задача следующая. Сделай осмысленный коммит с ID задачи, добавив только относящиеся к ней файлы. После этого самостоятельно переходи к следующей готовой задаче.
8. При продолжении сессии прочитай краткий актуальный контекст и точечно проверь код. Не полагайся на прежний статус без проверки реальных файлов. Если задача не закончена, продолжи с записанного следующего действия.

Обязательные границы:

- Сохраняй утверждённые data/, algorithm/models.py, algorithm/genetic/, algorithm/evaluation/, interface/, visualization/, tests/.
- ГА не импортирует NiceGUI, не рисует карту и не делает сетевые запросы. UI не содержит формулы и генетические операторы.
- Гены — направленные EdgeId `(u,v,key)`; валидация учитывает связность, A/B, направления, доступ, запреты, закрытия и циклы. Популяция строго N, копии ограничены, попытки конечны.
- Скрещивание по общей промежуточной вершине; две переключаемые мутации. Ремонт сейчас не реализуй, но оставь ясную точку его последующего подключения.
- Не подмешивай заранее найденный оптимальный маршрут в P0. Вспомогательный поиск между случайными промежуточными вершинами допустим и должен быть прозрачен.
- «Экономичный» — только минимизация длины. J минимизируется; эталоны фиксированы на запуск. J разных пресетов не является общей шкалой даже при общих эталонах: сравнивай L/T/C. Общая P0 остаётся открытым выбором Q07-C. Не обещай глобальный оптимум.
- Пробки 1–11, максимум покрытия определяет уровень ребра, равенство — больший балл. 11 — запрет движения, не деление на ноль. Не менять принятое правило короткого недоминирующего перекрытия.
- Правая панель: Настройки/Результаты. Независимые пресеты накапливают результаты только при неизменных общих условиях. Изменение условий — через подтверждение; отмена сохраняет всё; подтверждение очищает результаты, графики, поколения и воспроизведение. Архива нет.
- Сначала полный расчёт, потом анимация сохранённой истории. Перемотка/скорость не влияют на ГА или RNG.
- Не придумывай коэффициенты, пределы, скорость при неизвестном maxspeed или веса Лёгкого. Применяй принятые базы ограничений и техническую формулу разнообразия из DECISIONS. Q — группа: повторно не спрашивай ACCEPTED A/B; только нужные OPEN C блокируют соответствующие функции. PROPOSED (в частности окно стагнации 10 и общая P0) не является default. Приведи конкретный выбор пользователю и запиши принятое решение; тестовые числа не переносить в рабочие defaults.
- Не выдавай неизвестный дорожный признак за его отсутствие. Не обещай поддержку всех ПДД. Не включай реальные Traffic API, NSGA-II, топливную модель, базу данных, ремонт и экспорт сценариев без нового запроса.
- Не используй force push и не переписывай опубликованную историю без отдельного явного разрешения. Не публикуй секреты. Проверяй staged diff перед коммитом/push. Первый push входит в этап 0; режим дальнейших обычных push согласуй явно и соблюдай его.

Если встретишь препятствие, не прекращай всю работу автоматически. Отметь конкретную задачу BLOCKED, укажи причину и минимально необходимое решение. Продолжай независимые готовые задачи, сохраняя порядок UI-first. Не обходи блокировку произвольными коэффициентами или фиктивными результатами. Рутинные обратимые изменения в пределах этого запроса не требуют повторного разрешения.

Сообщай о ходе работы по-русски, кратко: какие файлы действительно изменены, что проверено, что осталось. Перед окончанием сессии обязательно обнови CURRENT_TASK.md: последний завершённый шаг, текущая ошибка/проверка, точное следующее действие. Не обещай бесконечную автономность; обеспечь восстановление работы без повторного чтения всей истории.

## Короткий промпт для продолжения

Продолжи GARoute в `C:\GARoute` с текущей задачи. Прочитай AGENTS.md, CURRENT_TASK.md, верхнее резюме PROGRESS.md, карточку активного ID и нужные решения. Проверь реальное состояние файлов/Git. Не перечитывай всё ТЗ и не начинай проект заново. Выполняй задачу до проверенного результата, обновляй статусы, делай осмысленный коммит и выбирай следующую готовую задачу. Соблюдай ранее установленный режим публикации и не подставляй неутверждённые параметры.
